## Q1. 서비스 기획 의도와 과정

### 스위트북에 맞춰 책 서비스를 만들지 않기로 한 것이 첫 결정입니다

과제는 주제가 자유롭다고 명시했습니다. 그래서 스위트북의 현재 제품을 모방하는 대신, 회사가
어느 방향으로 움직이는지부터 조사했습니다. AI Story Class와 Book Print API를 함께 놓고 보면
반복되는 구조가 보였습니다.

```
축적된 디지털 콘텐츠 → 구조화·큐레이션된 산출물 → (선택적) 물리적 결과물
```

이 구조를 **요구사항이 아니라 렌즈로만** 썼습니다. 목표는 스위트북과 닮은 것을 만드는 게 아니라,
그 자체로 독립적인 할 일(job-to-be-done)이 있는 콘텐츠 서비스를 찾는 것이었습니다.

### 후보를 죽이는 방식으로 골랐습니다

개발자 히스토리, 교육, 여행/라이프로그, 가족 기록, 크리에이터, 스포츠, 음식, 동아리, 게임
커뮤니티, 컨퍼런스, 포트폴리오, 회사/팀 히스토리, 온라인 커뮤니티까지 넓게 펼친 뒤, 각 후보에
대해 AI에게 **경쟁 서비스를 찾아 그 아이디어를 옹호하지 말고 공격하라**고 시켰습니다.

- **Repo Chronicle** (깃 히스토리 → 프로젝트 회고록)이 처음 유력했습니다. REST API 소스가
  자연스럽고, 콘텐츠 수명주기가 구조적이고, 스위트북 인접성도 그럴듯했습니다. 그런데 경쟁 조사에서
  Commit Story, wrapped류, GitRoll, 그리고 결정적으로 activity README 도구 · all-contributors ·
  Release Drafter · semantic-release 같은 **README/체인지로그 자동화**가 나왔습니다. 가치 제안이
  "깃 히스토리를 이야기로"에서 "사람이 큐레이션한 회고"로 계속 좁아졌고, 결국 "자동 생성되는 업적
  README 섹션"과 구분되지 않는 지점에 도달했습니다. **보류.**
- **Conference Afterbook** (행사 데이터 → 사후 발행물)은 살아남았지만, 한국 행사 시장에는 더 넓은
  플랫폼이 있고 사후 리포트·세션 콘텐츠 재활용·참가자 리캡이 이미 그 자리를 차지하고 있었습니다.
  가능하지만 통증의 증거가 약했습니다. **2순위.**

### 결정적 전환은 AI가 아니라 제가 만들었습니다

AI가 제안한 디스코드 아이디어는 "커뮤니티 정기 발행물"이었습니다. 저는 그 제안에서 흥미로운 부분은
발행이 아니라 **캡처 레이어**라고 다시 정의했습니다.

> 봇이 선택된 디스코드 메시지를 지속적인 저장소로 "클립"한다. P0는 저장소의 **생성**을 소유하고,
> 거기서 나중에 무엇을 발행할지는 소유하지 않는다.

이 재정의가 범위를 크게 줄이면서 동시에 독창성을 올렸습니다. 그리고 여기에는 실제로 겪은 문제가
있었습니다. 저는 디스코드 핀 한도에 부딪혀 **오래된 핀을 지워서 자리를 만들어 본 적이 있습니다.**
(현재 한도는 채널당 250개이므로, 제품은 낡은 100개 주장을 하지 않습니다. 중요한 건 숫자가 아니라
핀이 **채널에 갇혀 있고, 유한하고, 모더레이션 권한 중심**이라 공용 아카이브 역할을 못 한다는
점입니다.)

### 마지막으로 포지셔닝을 다시 공격했습니다

디스코드 핀, 개인 북마크, Starboard류 반응 임계 아카이브, Pin Archiver류 봇, 대량 로깅/익스포트
도구, Discord→Notion/Obsidian 워크플로를 조사한 결과 **"무제한 핀 아카이브"는 니치가 아니었습니다.**
그래서 의미론적 위치를 이렇게 확정했습니다.

> **공동체의 의도적 기억(shared intentional memory)** — 권한을 가진 멤버가, 먼저 핀을 찍지 않고,
> 인기 투표 없이, 서버를 통째로 삼키지 않고, 보이는 메시지 하나를 의도적으로 보존한다.

| 기존 원시 기능 | 그것이 뜻하는 것 |
|---|---|
| 디스코드 핀 | 모더레이터가 **이 채널에서** 중요하다고 말함 |
| 개인 북마크 | **내가** 나중에 보고 싶다고 말함 |
| Starboard | **충분히 많은 사람이** 좋아했음 |
| 핀 아카이버 | **이미 핀이었고** 넘쳤음 |
| 대량 로거 | **전부 담고** 나중에 거름 |
| **Clip** | **권한 있는 멤버가 커뮤니티를 위해 보존할 가치가 있다고 말함** |

### 코드를 만들기 전에 엣지 케이스를 먼저 닫았습니다

과제 안내가 요구사항 정의를 구현만큼 무겁게 본다고 했기 때문에, 구현 전에 다음을 전부 결정하고
스펙에 동결했습니다: 스냅샷 불변성, 작성자·관리자 삭제 권한, 역할 기반 클리핑 제한, 아카이브
비공개 기본값, 메시지 1개 한정, 중복 클립과 복수 보존 신호, 클립/언클립 동시 실행 경쟁, 작성자
알림, 마커 의미, 사전 옵트아웃 유예, 채널 차단 목록 유예, **디스코드=콘텐츠 평면 / PostgreSQL=제어
평면**, Gateway 대신 HTTP 인터랙션, 설정·인증 흐름, 관리자 전용 웹 아카이브, 배포 제약과 비용.

이 중 마지막에서 두 번째 항목이 이 제품의 중심 결정입니다.

| 디스코드가 권위를 갖는 것 | PostgreSQL이 권위를 갖는 것 |
|---|---|
| 보관된 메시지 본문 | 길드 설정과 허용 역할 |
| 임베드·첨부·미디어 | Clip 동일성과 상태 기계 |
| 스냅샷 렌더링 | 사용자별 보존 신호 |
| 사용자/채널 표시 정보 | 작성자·관리자 삭제 툼스톤 |

Clip은 메시지 본문, 첨부 바이너리, 임베드 페이로드를 **절대 저장하지 않습니다.** 저희 데이터가
전부 사라져도 커뮤니티가 소유한 콘텐츠는 그대로 남아야 하기 때문입니다.

## Q2. MVP 범위를 그렇게 정한 근거

### 기준은 "기능 개수"가 아니라 "이게 없으면 서비스가 틀리게 동작하는가"였습니다

P0에 넣은 항목은 12개이고, 전부 같은 질문을 통과했습니다. **빼면 제품이 작아지는 게 아니라,
잘못 동작하거나 사용자에게 해를 끼치는가?**

| P0 항목 | 없으면 무엇이 깨지는가 |
|---|---|
| 관리자 설정 + 아카이브 목적지 | 보관할 장소 자체가 없음 |
| 역할 기반 `Apps → Clip` | 아무나 남의 발언을 공용 기록에 올림 — 동의 문제 |
| 선택한 메시지 1개 한정 | 범위가 불명확해지고 동의 경계가 무너짐 |
| 정규 중복 제거 + 복수 보존 신호 | 같은 메시지가 아카이브에 여러 번 쌓임 |
| 언클립 의미론 | 되돌릴 수 없는 캡처는 동의를 깨뜨림 |
| 작성자/관리자 삭제 + 툼스톤 | 삭제해도 즉시 다시 클립되는 루프가 생김 |
| 동시성·멱등성·상태 기계 | 경쟁 조건에서 조용히 데이터가 틀어짐 |
| 아카이브 비공개 기본값 | 비공개 채널 발언이 공개로 새어나감 |
| 작성자 DM + 원본 마커 | 당사자가 모르는 사이 보존됨 |
| 최소 PostgreSQL 제어 평면 | 상태를 둘 곳이 없음 |
| 읽기 전용 관리자 웹 아카이브 | 운영자가 무엇이 보관됐는지 확인할 수 없음 |
| 실제 배포 | 디스코드는 진짜 HTTPS 엔드포인트만 받음 |

동의와 관련된 항목이 유난히 많습니다. 이 제품은 **다른 사람이 쓴 글을 그 사람의 사전 동의 없이
공용 기록으로 옮기는** 제품이라, 캡처보다 사후 통제(알림·마커·본인 삭제·툼스톤)가 더 중요하다고
판단했습니다.

### 뺀 것은 15개이고, 각각 이유가 다릅니다

전체 표는 스펙 §21에 있고, 유예 사유는 세 종류로 묶입니다.

1. **니치를 무너뜨리기 때문에 뺀 것** — 반응 기반 클리핑(Starboard가 됨), AI 요약·클러스터링
   (사람의 클리핑 결정 자체가 의미 신호인데 AI가 그걸 대체하면 검증할 게 없어짐).
2. **저장 책임이 늘어나기 때문에 뺀 것** — 전문 검색, 콘텐츠 캐시, 미디어 사본. 전부 "본문을
   저장하지 않는다"는 소유권 경계를 깨야만 가능합니다.
3. **오늘은 더 싼 올바른 층이 있어서 뺀 것** — 권한 인식 아카이브 라우팅(→ 비공개 채널로 충분),
   사전 옵트아웃(→ 사후 삭제로 충분), Gateway 워커(→ HTTP 인터랙션으로 충분), 회원 OAuth
   (→ 짧은 관리자 세션으로 충분).

세 번째 묶음이 이 프로젝트의 범위 원칙입니다. **오늘 가장 싼 올바른 층을 고르고, 폴리시 로드맵은
따로 적어 둔다.** 잘못된 층을 고르면 나중에 마이그레이션이 필요하지만, 싼 층을 고르는 건 나중에
얹으면 되기 때문입니다.

### 그리고 마감이 실제로 범위를 한 번 더 잘랐습니다 — 이건 계획대로 된 게 아닙니다

마감 23시간 전, 남은 그래프를 프로젝트 자신의 실측 속도(Wave 1 ≈ 6시간, Wave 2 ≈ 10시간)에
대고 계산했더니 **23시간에 36~60시간치 작업**이 남아 있었습니다. 계획서에 적어둔 컷 순서는 26개 중
5개만 제거해서 이 격차를 못 메웠습니다.

그래서 다음 노드를 잡고 진도를 내는 대신 산수를 그대로 보고했고, 저는 **디스코드 경로 전체 +
최소 설정 UI**를 지키기로 결정했습니다. 잘라낸 것:

- **Wave 5 전체 — 읽기 전용 웹 아카이브.** 위 표의 11번, 즉 P0로 승인했던 항목입니다.
  계획서의 컷 순서에도 없던 항목이라 **승인 범위의 실질적 축소**입니다. 디스코드 아카이브 채널
  자체가 이미 내용을 보여주므로 잃는 것은 편의이지 제품이 아니라고 판단했고, 화면 D/E는 최종
  디자인과 한국어 카피로 `06_DESIGN_HANDOFF.md`에 남아 있습니다. 다만 **목업은 구현이 아니며**
  이 문서는 그것을 구현으로 세지 않습니다.
- 역할 설정 UI(`4.3`) — 스펙이 관리자 전용 클리핑을 이미 허용합니다. 그래서 출시본은 관리자만
  클립할 수 있습니다.
- Playwright E2E(`6.4`), 전면 접근성 감사(`7.1`).

**절대 자르지 않은 것:** 행 잠금과 상태 기계, 작성자·관리자 삭제와 툼스톤, 비공개 기본값, 배포.
정확성·동의·배포는 컷 대상이 아니라는 규칙을 프로젝트 시작 때 문서에 적어 두었고, 마감 압박
아래에서 그 규칙이 실제로 결정을 내렸습니다.

## Q3. 바이브코딩 수행 과정

### 한 문장

**AI는 연구자·적대적 리뷰어·아키텍처 옵션 생성기, 그리고 나중에는 구현자로 썼습니다.
제품 판단은 넘기지 않았습니다.**

### 실제 작업 흐름

```
스펙 동결 → DAG로 원자 단위 태스크 분해 → wave당 브랜치 1개 / PR 1개
  → 실패하는 테스트 먼저 → 구현 → 뮤테이션으로 테스트가 정말 실패하는지 확인
  → 쓰지 않은 별도 에이전트가 전체 브랜치 리뷰 → 사람이 판정
  → CI(lint/test/build) → 머지 → 스냅샷에 증거 append
```

숫자로: 커밋 112개, 머지된 PR 5개, 테스트 **345개 / 30개 파일 전부 통과**(동시성은 목이 아니라
실제 PostgreSQL 17), 배포는 `main` HEAD 커밋과 동일한 이미지가 k3s에서 실행 중.

### 구체적으로 AI를 어떻게 다뤘는지

**1. 제품 의미론을 코드 생성 전에 동결했습니다.** 구현 에이전트는 "무엇을 만들지"가 아니라
"어떻게 만들지"만 최적화합니다. `CLAUDE.md`에 **"확정된 제품 의미론을 재설계하지 말 것"**을
규칙으로 박아두었고, 애매하면 추측하지 말고 물어보라고 지시했습니다. 실제로 구현 에이전트가
디자인 토큰 충돌을 발견했을 때 스스로 판단하지 않고 에스컬레이션했습니다 — 그리고 그때 제가 내린
판정이 틀렸습니다(Q4 참조).

**2. 검증을 AI에게 위임하되, 검증 방법 자체를 의심했습니다.** 이 프로젝트에서 가장 많이 쓴 기법은
**뮤테이션 테스트**입니다. 테스트가 통과한다는 사실은 아무것도 증명하지 않습니다. 고의로 버그를
다시 집어넣었을 때 그 테스트가 **실패하는 것을 눈으로 본** 것만 증거로 인정했습니다. 이 규칙이
실제로 잡아낸 것:

- `/setup` 핸들러를 서명 검증 **위로** 옮겼는데 71개 테스트가 전부 통과했습니다. 인증 없는 POST가
  임의 길드의 관리자 세션 토큰을 발급받을 수 있는 상태였고, 기존 401 테스트들은 `{type:1}`만
  보내서 그 분기에 아예 들어가지 않았습니다.
- 자동 생성 아카이브 채널에서 `@everyone` 거부 오버라이트를 통째로 지웠는데 307개가 전부
  통과했습니다. "비공개 기본값"이라는 P0 항목에 테스트가 하나도 없었던 것입니다.

**3. 쓴 사람과 읽는 사람을 분리했습니다.** wave 전체 리뷰는 구현에 참여하지 않은 별도 에이전트가
전체 diff·계획·판정 기록을 받아서 수행합니다. 지시문에 **"컨트롤러가 이 영역 상당수를 직접 썼거나
판정했으므로 그것을 검증하기에 가장 부적합한 사람"**이라고 명시적으로 적었습니다. Wave 3 리뷰는
Critical 3건을 냈는데, 제가 위험하다고 지목했던 세 영역(인가, 교차 길드 쓰기, 콘텐츠 유출)은 전부
깨끗했고 **지적은 전부 제가 볼 생각을 안 한 곳에서 나왔습니다.**

**4. 리뷰 결과도 그대로 받지 않았습니다.** 코드 리뷰 지적 11건을 받았을 때 구현 전에 하나씩
코드베이스에 대고 확인했습니다. 그중 하나(`DISCORD_APPLICATION_ID`가 봇 유저 ID가 아니라는 지적)는
실제 디스코드 API에 `GET /users/@me`를 쳐서 두 값이 동일함을 확인하고 **근거와 함께 반려**했습니다.

**5. 기록을 실시간으로 남겼습니다.** 기술 노트는 저널에, 과제 증거는 append-only 스냅샷에
그때그때 적었습니다. 사후에 정리하지 않은 이유는 Q4의 첫 사례 때문입니다 — 관찰이 컨텍스트에만
있으면 그건 증거가 아닙니다.

### 무엇이 잘 안 됐는지도 워크플로의 일부입니다

병렬 서브에이전트는 같은 파일을 건드리면 충돌하기 때문에 파일 소유권으로 직렬화해야 했고, 두
에이전트는 세션 한도로 작업 도중 죽어서 결과를 인계받아 직접 마무리해야 했습니다. AI 오케스트레이션은
공짜 병렬화가 아니라 **관리해야 하는 자원**입니다.

## Q4. AI 도구를 사용하면서 겪은 실패 또는 문제

스냅샷에 기록된 실패는 여러 건이지만, 서로 다른 사건이 아니라 **같은 실패의 다른 각도**라는 게
이 프로젝트의 결론입니다. 세 개를 골라 적습니다.

### 사례 1 — AI가 재현할 수 없는 사실을 README에 적었습니다

AI가 k3s 노드가 4코어에서 부하 평균 14로 지속 실행 중이라고 보고했습니다. 그리고 그 원인을
**같은 노드에 있는 특정 타인의 워크로드(`ssemtle`)가 리소스 요청을 선언하지 않은 탓**으로 지목하고,
그 워크로드의 파드 두 개가 무작위 이름의 바이너리(`./javae`, `./ycxm7ue3qrco`)를 재생성하고 있다고
— 사실상 침해를 시사하며 — 보고했습니다. 그 위에 부하 수치를 **공개 README에 사실로 적고**,
이슈 2개(`0.2`, `0.3b`)를 `blocked:human`으로 막았습니다. 즉 AI가 **제3자의 워크로드에 대한
사실 주장을 공개 저장소에 게시**한 것입니다.

저는 받아들이지 않고 이렇게 요구했습니다. *"`ps` 같은 명령으로 그 주장의 증거를 제가 직접 찾을 수
없습니다. 제가 확인할 수 없으면 판단을 신뢰할 수 없으니, 커맨드라인이나 안티바이러스 해법을
주세요."* 제가 root로 직접 돌린 결과: 부하는 1.42/1.94/4.02였고, 15분 수치는 **제가 그때 돌리고
있던 ClamAV 스캔**(CPU 80.7%)으로 전부 설명됐습니다. CPU 5%를 넘는 프로세스는 `clamscan`과
`k3s server` 둘뿐, 보고된 바이너리는 어느 컨테이너 파일시스템에도 없었습니다.

**진짜 실패는 오진이 아니라 증거 처리입니다.** 게다가 그 오진의 대상은 저희 것이 아닌 남의
워크로드였고, 그것을 공개된 곳에 적었습니다. 원래 관찰은 세션 스크래치패드와 AI의 컨텍스트에만
있었고, 주장이 반박당한 시점에는 둘 다 사라진 뒤였습니다. 그래서 **맞았는지 틀렸는지 판정할 방법이
아예 없습니다.** AI의 관찰은 원시 출력과 함께 적히기 전까지 증거가 아닙니다. AI가 "봤다"고 기억하는
것은 남지 않기 때문입니다. 이 프로젝트가 증거를 실시간으로 파일에 적게 된 계기가 이 사건입니다.

### 사례 2 — 통과할 수 없는 검증과, 실패할 수 없는 테스트

동시성 테스트를 하나 만들었습니다. 설정 토큰 하나를 N개 요청이 동시에 교환하려 할 때 정확히
하나만 성공하는지 보는 테스트입니다. 구현자가 자기 테스트를 믿지 못해서, 그 테스트가 잡으라고
만들어진 바로 그 버그(read-then-write)를 일부러 집어넣었습니다. **테스트는 그대로 통과했습니다.**

원인은 커넥션 풀이었습니다. `node-postgres` 풀은 커넥션을 게으르게 엽니다. 첫 호출자는 9ms 만에
읽기-쓰기를 끝냈고 나머지는 그때까지 TCP·인증 핸드셰이크 중(22ms)이었습니다. **호출자들은 DB
수준에서 한 번도 동시였던 적이 없어서**, 깨진 구현이 관찰할 경쟁 자체가 없었습니다. 풀을 미리
데우자 10/10으로 결정적으로 실패했습니다.

여기서 더 나쁜 두 번째 층이 나옵니다. 나중에 "고친 것마다 되돌려서 테스트가 실패하는지 보자"는
검증을 돌렸는데, 방법이 **커밋 통째로 revert**였습니다. 커밋을 되돌리면 그 커밋이 추가한 **테스트도
같이 사라지므로**, 되살아난 버그를 잡을 주체가 남지 않습니다. 세 번 다 "깨끗함"으로 읽혔습니다.
그리고 그 밑에 또 한 층 — 로컬 도커의 디스크가 차서 Postgres 컨테이너가 죽어 있었고, 307개 중
89개가 단언 실패가 아니라 **커넥션 에러**로 실패하고 있었습니다. 실패를 좋은 소식으로 읽는
기법에서는, 죽은 DB가 노이즈가 아니라 **위양성 생성기**가 됩니다.

여기서 얻은 규칙은 좁고 기계적입니다. **테스트의 실패가 원하는 증거일 때는, 실패 개수가 아니라
실패 이유를 읽을 것.** 단언 에러와 커넥션 에러는 요약 줄에서 같은 빨간색이고 정반대를 뜻합니다.

### 사례 3 — 엄밀한 검증이, 주장 대상 바로 옆을 겨눴습니다

이게 이 프로젝트에서 가장 많이 반복된 실패이고, 게으름이 아니라 **성실함의 실패**라서 적습니다.

Wave 3에서 마이그레이션 initContainer를 추가하고, 로컬에서 빌드한 이미지에 대고 7가지를
확인했습니다. 빈 DB에 마이그레이션 적용, 테이블 7개 생성, 재실행 시 pending 없음, 서버 부팅,
`/api/health` 응답. **전부 진짜로 돌린 검사입니다.** 그런데 `k8s/deployment.yaml`은 그 이미지를
가리키고 있지 않았습니다. 매니페스트는 **브랜치 시작점 커밋의 태그**에 고정돼 있었고, 그 이미지에는
애초에 `/migrate` 경로가 없습니다 — 마이그레이션 스테이지를 추가한 게 바로 이 브랜치이기
때문입니다. 머지된 매니페스트를 적용했다면 서비스가 낡아지는 정도가 아니라 `Init:CrashLoopBackOff`로
**내려갔을 것**입니다. 리뷰어의 표현이 정확했습니다. *"이것이 '빌드한 이미지에서 검증했다'가
놓치는 것이다. 당신이 검증한 이미지는 YAML이 지목하는 이미지가 아니기 때문이다."*

같은 형태가 같은 날 두 번 더 나왔습니다. 배포가 막혔다고 보고했을 때, 실제로는 **접근 경로**만
찔러봤을 뿐 원하는 최종 상태를 확인하지 않았습니다 — 인증 없는 `curl https://clipendpoint.cc/api/health`
한 번이면 0.4초 만에 반증됐고, 서비스는 이미 7시간째 정상 서비스 중이었습니다. 그리고 콜아웃 색상
판정에서는, 디자인 원본 대신 그것을 요약한 **두 개의 요약본**(토큰 파일과 핸드오프 표)만 비교해서
판정했습니다. 두 요약본은 같은 방향으로 정보를 잃었기 때문에, 아무리 신중하게 비교해도 답이 나올 수
없었습니다. 원본에 `grep` 한 번으로 끝났습니다.

**공통 형태:** 작업은 성실했고, 증거는 진짜였고, 결론은 틀렸습니다. 엄밀함이 주장하려는 대상에서
한 칸 옆에 적용됐기 때문입니다. 그래서 초록색 결과를 믿기 전에 던지는 질문 하나를 규칙으로
만들었습니다. **내가 정확히 무엇을 관찰했고, 그것이 내 주장의 대상과 같은 물건인가?**

### 그리고 구조적으로, 매번 같은 방식으로 잡혔습니다

보류된 결함, 되살아난 가드, 거짓 블로커, 내려갔을 배포 — **전부 그것을 쓰지 않은 사람이
잡았습니다.** 자기 검증이 여기서 계속 실패하는 이유는 엄밀함이 부족해서가 아니라, 검증자와
피검증자가 같은 환경을 공유하는데 그 환경이 자기 건강 상태를 보고하지 않기 때문입니다. AI를
쓰는 워크플로에서 **읽는 사람과 쓰는 사람을 분리하는 것**은 스타일 문제가 아니라 이 실패 모드에
대한 유일하게 작동한 대책이었습니다.
