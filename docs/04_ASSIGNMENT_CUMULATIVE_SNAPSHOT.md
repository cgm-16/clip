## 서비스 기획 의도와 과정

> 이번 과제에서 본인이 만든 콘텐츠 서비스를 왜 이렇게 기획했는지, 어떤 과정을 거쳐 기획을 구체화했는지 작성해 주세요.

## Current evidence snapshot

### A. Starting point — do not force a book-themed product

`DECISION`

The assignment explicitly allowed a free topic unrelated to printing/books. The planning therefore started by researching Sweetbook's actual strategic position rather than cloning its current products.

Research reframed Sweetbook from a loose “traditional publisher” description into a more precise vertically integrated digital-print/POD/software company. AI Story Class and Book Print API suggested a repeated structural pattern:

```text
digital/accumulated content
-> structured/curated output
-> optional durable/physical artifact
```

This became a lens, not a requirement. The goal was to find a content service with a real independent job-to-be-done.

### B. Broad domain exploration

`FACT / DECISION`

Domains considered included developer history, education, travel/lifelog, family memory, creators/newsletters, sports, food, clubs, gaming communities, conferences/events, professional portfolios, company/team history, and online communities.

Competitor maps were used to attack rather than merely validate ideas.

### C. Repo Chronicle was initially favored, then parked

`AI_PROPOSAL -> HUMAN_OVERRIDE / RESEARCH`

Initial idea:

> GitHub repository history -> curated project retrospective -> web/PDF/optional physical project book.

Why it looked good:

- natural REST API source;
- structured content lifecycle;
- developer-domain authenticity;
- plausible Sweetbook adjacency.

Competitor research found Commit Story, wrapped-style GitHub products, GitRoll/GitHubFolio, repo visualizers, and then README/changelog automation such as activity README tools, all-contributors, generated release notes, Release Drafter and semantic-release.

The broad value proposition kept narrowing from “Git history into a story” to “human-curated project retrospective.” The user explicitly noticed that the altered version risked becoming an automated accomplishments/acknowledgements README section. This was treated as evidence that the core job was too crowded/commoditized for the test.

**Outcome:** parked, not selected.

### D. Conference Afterbook was tested and downgraded

`AI_PROPOSAL -> RESEARCH -> DECISION`

Concept:

> structured event data -> attendee/session enrichment -> finished post-event publication.

Sessionize was researched as connector #1 rather than as the whole market. The Korean event market has broader platforms, and adjacent post-event jobs were already occupied by event reports, session-content repurposing, attendee recap tools and academic proceedings.

The idea remained viable but had weaker direct evidence of painful demand.

**Outcome:** fallback, not selected.

### E. Community Issue changed into the actual product primitive

`HUMAN_OVERRIDE`

The initial AI framing was a recurring community publication. The user reframed the interesting job as the **capture layer**:

> A bot “clips” selected Discord messages into a persistent repository, similar to the clipping metaphor in streaming culture. P0 owns creation of the repository, not what later gets published from it.

This was a major simplification and improved originality.

### F. Personal pain became the strongest signal

`FACT`

The user had genuinely encountered Discord pin limits and had to delete older pinned messages to make room. Current Discord documentation now allows 250 pins per channel/DM, so the final product does **not** claim an outdated 100-pin limit. The important lived problem is that pins remain bounded, channel-local and moderator-oriented rather than serving as a durable shared archive.

### G. Competitor attack changed the positioning again

`RESEARCH / DECISION`

Existing products include:

- Discord Pins;
- personal bookmarks;
- Starboard/reaction-threshold archives;
- Pin Archiver-style bots;
- bulk Discord logging/export tools;
- Discord-to-Notion/Obsidian workflows.

This invalidated “unlimited pin archive” as the niche.

Final semantic position:

> **Shared intentional memory:** an authorized member deliberately preserves one visible message into a server-owned archive, without first pinning it, without popularity voting, and without bulk ingesting the server.

### H. Product/architecture was pressure-tested before implementation

`DECISION`

The planning then explicitly resolved:

- immutable snapshot vs mirror;
- author/admin removal rights;
- role-gated clipping;
- private archive visibility;
- one-message-only P0 scope;
- duplicate clipping and multiple preservation signals;
- simultaneous clip/unclip races;
- author notification;
- status marker semantics;
- preemptive opt-out deferral;
- channel denylist deferral;
- Discord content plane vs PostgreSQL control plane;
- HTTP interactions vs persistent Gateway;
- setup/auth flow;
- admin-only web archive;
- deployment constraints and cost.

This is part of the answer: the planning intentionally attacked edge cases before code generation because the assignment weights requirements/product definition heavily.

# Assignment Question 2

## MVP 범위를 그렇게 정한 근거

> 기획한 서비스가 운영되려면 무엇이 최소로 필요하다고 판단했는지, 그리고 왜 그렇게 판단했는지 작성해 주세요.  
> 이번 범위에 넣은 것만큼 넣지 않은 것도 함께 적어주세요. 무엇을 뒤로 미뤘고 그 이유가 무엇인지가 이 문항의 핵심입니다.

## Current evidence snapshot

### P0 thesis

`DECISION`

> P0 must prove that a community can configure archival authority, intentionally clip one message, preserve it canonically without duplicates, respect author/admin removal, and browse the resulting archive — while remaining deployable and operable under real Discord/API conditions.

### Included because the service cannot operate correctly without them

#### 1. Admin setup + archive destination

- `/setup` from Discord;
- short-lived signed admin web session;
- create private archive or select existing channel;
- configure roles;
- admins implicitly allowed.

Reason: without configuration there is no trusted destination/authority boundary.

#### 2. Role-gated `Apps -> Clip`

Reason: making every member an archivist by default creates immediate abuse/privacy risk.

#### 3. One selected message only

Reason: explicit target is the smallest consent/scoping unit. Automatically including replies/threads silently archives other people's content.

#### 4. Canonical deduplication + multiple clipper signals

Reason: multiple members may select the same message. Duplicate archive posts are bad UX; ignoring the second user's intention would lose useful state.

#### 5. Unclip semantics

Reason: preservation should represent a continuing user decision. One user retracting their signal must not remove a clip another user still wants preserved.

#### 6. Author/admin removal + durable tombstone

Reason: immutable snapshots without revocation create abuse risk for ordinary users. Removal must also prevent immediate recreation by another clipper.

#### 7. Concurrency/idempotency/state machine

Reason: double-clicks, retries and simultaneous users are normal distributed-system conditions; without transactional rules the service could create duplicate Discord posts or delete an archive incorrectly.

#### 8. Private archive default

Reason: clipping from a private source into a public archive could silently escalate visibility. P0 chooses the safest simple default rather than attempting full permission-graph mirroring.

#### 9. Best-effort author DM + persistent marker

Reason: an author removal right is weak if authors cannot discover that archival happened. DM is targeted but not guaranteed, so a source marker and native removal command provide another path.

#### 10. Minimal PostgreSQL control plane

Reason: configuration, clipper signals, tombstones, concurrency state and notification idempotency are genuine product state. Trying to encode all of this into Discord merely to avoid a DB made the design more fragile.

#### 11. Read-only admin web archive

- newest-first;
- pagination;
- source-channel filter;
- live Discord fetch.

Reason: assignment asks for a content-service web application; the browser proves cross-channel archive consumption without duplicating content into our DB.

#### 12. Real deployment

Reason: Discord HTTP interaction endpoints, permissions, DNS/HTTPS and DB behavior must work in the real environment; localhost-only implementation is not an operable service.

### Explicitly deferred and why

| Deferred | Reason |
|---|---|
| AI summarization/clustering | The human clipping decision is the valuable semantic signal; AI is not needed to validate capture. |
| Community magazine/yearbook/print | Downstream use of the corpus; would distract from validating archive creation. |
| Book Print API | Relevant roadmap, not required for independent P0 value. |
| Full-text/semantic search | Would require content indexing/caching/storage expansion. |
| Tags/collections | Useful after corpus exists; not necessary to prove capture. |
| Parent/thread clipping | Expands consent and privacy scope. |
| Reaction-driven clipping | Risks collapsing niche into Starboard/popularity semantics. |
| Preemptive user opt-out | Creates durable personal settings/policy plane; author removal is sufficient P0 safeguard. |
| Per-channel denylist | Additional configuration surface; private archive + role gate accepted for P0. |
| Permission-aware archive routing | Correct but complex Discord permission-graph problem. |
| Member-facing OAuth web archive | Adds OAuth/token/session/role-sync security surface. |
| Persistent content cache | Live REST fetch is cheaper/correct enough at P0 scale. |
| Discord Gateway worker | Explicit HTTP commands/buttons are sufficient; Gateway only needed for ambient events. |
| Automated reconciliation | Define recoverable state now; build full repair/WAL tooling later. |
| Hosted message/media copies | Adds storage/privacy/scaling burden without increasing core value. |

### Important scope principle

`DECISION`

The team repeatedly chose the cheapest correct layer today and documented the polish roadmap separately:

- live fetch now -> short-lived cache later;
- private archive now -> permission-aware routing later;
- post-capture author control now -> preemptive preference plane later;
- explicit context command now -> reaction shortcuts later;
- HTTP interactions now -> Gateway worker later.

## Planning-stage failures already available

These are genuine candidate examples even if implementation later provides stronger ones.

### Failure candidate A — first recommendation was under-researched

`AI_PROPOSAL / HUMAN_OVERRIDE`

AI initially recommended Repo Chronicle as the strongest concept before enough direct-competitor research had been performed.

The user liked the idea but explicitly asked for deeper market/competitive research. Once challenged:

- Commit Story already occupied “Git history -> story”;
- README/changelog automation occupied much of “automated accomplishments/current project narrative.”

The idea had to be repeatedly narrowed and was eventually parked.

**Problem:** AI can generate a coherent-looking product position before sufficiently testing whether the core job is already commoditized.

**Detection:** human reduction test — “is this basically an accomplishments/acknowledgements README automation?” — plus targeted competitor search.

**Response:** convert AI from ideation mode into adversarial competitor research; reject the first attractive concept instead of defending it.

**Lesson:** use AI to attack its own proposal and require a crisp answer to “X already does this; what is our niche?” before implementation.

### Failure candidate B — stale pin-limit assumption

`AI/USER MEMORY -> WEB VERIFICATION`

The conversation initially treated Discord's pin limit as roughly 100 based on historical/user experience. Current official docs show 250 pins per channel/DM.

**Problem:** product rationale built on a remembered platform constraint can become stale.

**Detection:** explicit current-doc verification.

**Response:** stop positioning the product around a numerical 100-pin limit. Use the stronger durable problem: pins remain bounded, channel-local and moderator-oriented.

**Lesson:** volatile platform limits/API behavior must be verified against current official docs, even when the historical experience is real.

### Failure candidate C — over-optimizing for a disposable database

`AI_PROPOSAL -> DESIGN REVISION`

Early architecture tried to keep PostgreSQL as a reconstructable index and make the Discord archive channel behave almost like a WAL/source of truth for everything.

As concurrency, multiple clippers, author tombstones and notification idempotency were defined, this became strained. Later deployment analysis showed a PostgreSQL-backed always-available service was already necessary/acceptable.

**Problem:** AI optimized around an assumed “zero infra” goal longer than the actual product constraints justified.

**Detection:** revisit permanent state after accepting deployment/DB infrastructure; identify state that cannot be faithfully reconstructed from message content (clipper signals, consent tombstones).

**Response:** simplify the boundary: Discord owns content; PostgreSQL owns product/control state.

**Lesson:** do not preserve an architectural purity goal after its original constraint disappears.

### Failure candidate D — assuming a traditional always-on Discord bot

`ASSUMPTION -> DOC VERIFICATION`

The architecture initially discussed “hosting the bot” as if a long-lived Gateway/WebSocket process were mandatory.

Current Discord interaction docs allow explicit message-context commands/buttons to be delivered through an HTTPS interaction endpoint, so P0 can remain a stateless web/API service without a Gateway worker.

**Problem:** default mental model (“Discord bot = always-on gateway process”) added unnecessary infrastructure.

**Detection:** inspect current Discord interaction architecture once hosting cost became a concrete question.

**Response:** keep Gateway as P1 only if ambient reaction/channel events are introduced.

**Lesson:** verify platform primitives before accepting familiar architecture patterns.

**Task:** Repository preparation — verify the plan against the real Discord API before writing code.

**AI/tool used:** Claude Code (Opus 5), orchestrator session. Discord developer documentation and
the `discord-api-docs` repository consulted directly rather than answered from model memory.

**Human instruction/constraint:** Prepare the repo before implementation; ask about vague choices
rather than assuming; do not redesign settled product semantics.

**AI proposal/output:** The approved specification (§6.3, written during planning) instructed the
implementer to forward the selected message *and* wrap it in human-readable provenance metadata —
author, source channel, original timestamp, source link, clip timestamp — in a single archive post.
The implementation plan carried this forward as a single `archive_message_id` on the Clip row.

**Rejected/changed:** The single-post archive representation, and the schema that encoded it.

**Why:** Discord rejects it. A message carrying `message_reference.type = 1` (FORWARD) cannot also
carry `content`, `embeds` or `components`; the API returns error `160011`
(`Forward messages cannot have additional content`). The design is not merely awkward — it is
unbuildable. Three related constraints surfaced in the same check:

- `message_snapshots` is a minimal object that **excludes `author`**, so provenance genuinely
  cannot be recovered from the forward and must come from the control plane;
- creating a forward requires `VIEW_CHANNEL` on the *source* channel (error `160014`), making it a
  steady-state permission rather than the bootstrap-only concern §15 implied;
- only `DEFAULT`, `REPLY`, `CHAT_INPUT_COMMAND` and `CONTEXT_MENU_COMMAND` messages are
  forwardable, so polls, calls, activities and system messages need an explicit rejection path
  that no document previously specified.

**Accepted:** An archive entry became **two Discord messages** — a provenance message followed by
the forward — with both identifiers stored on the canonical Clip. The human chose this over three
alternatives (forward-only with provenance rendered from Postgres; a single embed copying the
content; provenance in a thread) because it preserves both the in-Discord reading experience and
the native snapshot payload.

**Validation/evidence:** Discord Message Resource documentation and docs PR #6818. Not yet
validated against a live guild — that is Wave 3 work, and this entry will be updated with the
observed result rather than replaced.

**Impact on Q1/Q2/Q3/Q4:** Primarily **Q4**, and it is a better example than the planning-stage
candidates already recorded, because the failure was produced by AI planning, caught by a
documentation check rather than by a runtime error, and corrected before it cost implementation
time. Secondarily **Q3**: the process rule that produced the catch was "verify platform primitives
against current documentation before accepting a plan that depends on them" — the same rule that
earlier corrected the stale 100-pin assumption (Failure candidate B) and the always-on Gateway
assumption (Failure candidate D). Three of four recorded failures now share one root cause:
**AI-authored designs that assume platform behavior instead of checking it.**

**Downstream changes:** `01_CLIP_PRODUCT_SPEC.md` §6.3 (two-message representation, forwardable
types), §8.3 (`archive_provenance_message_id` + `archive_forward_message_id`), §15
(`VIEW_CHANNEL` steady state), §17 (new failure cases 19 and 20), §5.1 (token TTL aligned to the
final Korean copy at 15 minutes). `DESIGN_RATIONALE_APPEND.md` §10. No visual design change: the
Screen D card hierarchy is unaffected because its source line was always going to be rendered from
control-plane data.

**Task:** Task 0.1 — make the Wave 0 container image actually serve `/api/health`.

**AI/tool used:** Claude Code (Opus 5), orchestrator session, writing the Dockerfile and diagnosing
the resulting crash.

**Human instruction/constraint:** Deployment is P0 work and happens before the product is built.
The image must run as a non-root user.

**AI proposal/output:** The first image built and started, then died immediately:

```
Error: Cannot find module '/app/node_modules/.pnpm/next@16.3.1_.../node_modules/
@swc/helpers/esm/_interop_require_default.js'
```

The AI diagnosed this as pnpm's symlinked `.pnpm` store defeating Next's standalone file tracing,
added `--node-linker=hoisted` to the image's install step, and **wrote that diagnosis into a
Dockerfile comment as settled fact** — before rebuilding, because the host disk had filled and the
rebuild was blocked. The commit message did flag the container test as unverified.

**Rejected/changed:** The diagnosis, and the comment asserting it.

**Why:** It was wrong, and one command would have shown it. Once the rebuild ran, inspecting the
builder stage showed `node_modules/@swc/helpers` was already a **real directory containing `esm/`**
— the hoisted linker had done exactly what was asked — and the crash persisted anyway. The traced
copy in `.next/standalone` contained **only `package.json`**. Tracing had not failed to *follow*
the package; it had copied the package and dropped every file in it. Next's own `require-hook.js`
resolves `@swc/helpers/esm/*` through the package's `exports` map at runtime, and the tracer cannot
see subpaths reached that way.

**Accepted:** `outputFileTracingIncludes: { '/**/*': ['./node_modules/@swc/helpers/**'] }` in
`next.config.ts`. `--node-linker=hoisted` was kept, but for the honest reason — the include glob
then resolves against real directories rather than symlinks — and the comment was corrected to say
so instead of restating the wrong cause.

**Validation/evidence:** Image rebuilt; container starts; `GET /api/health` returns `{"ok":true}`;
process runs as `uid=1001(nextjs)`. `pnpm lint` and `pnpm test` (7/7) green. Commit `f384318`.
