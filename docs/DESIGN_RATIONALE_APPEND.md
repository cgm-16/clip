## 1. 채택한 시각 방향

**계기판 (Instrument panel).** 근단색 그래파이트 표면, 1px 헤어라인, 2px 라운드, 기계값 전용 모노스페이스, 액센트는 상태 표시에만 사용.

- 서체: Pretendard (한글 UI 표준, P0는 한국어 전용 · i18n은 P1) + JetBrains Mono (채널·역할·시각·권한 상수·명령어)
- 액센트: `#4A5A8C` (라이트 테마 `#3F5185`) — 슬레이트 블루. 계측기 계열이며 Discord 브랜드 색과 혼동되지 않음
- 그림자 없음. 깊이는 선 1단계 + 표면 색 1단계로만 표현
- 테마: 다크 canonical, 라이트는 동일 토큰의 값 교체

근거: 제품 성격이 "조용한 보존 유틸리티"이므로 화면은 기록을 읽는 표면이어야 하고, 크롬은 존재감을 최소화해야 한다. 인기 순위·감시 로그·AI 마법·크리에이터 이코노미 어느 쪽으로도 읽히지 않는 시각 언어가 필요했다.

## 2. 검토했으나 기각한 방향

| 방향 | 내용 | 기각 이유 |
|---|---|---|
| 판 (Panel) | 슬레이트 액센트를 적극 사용, 카드 크롬 제거, 10px 라운드, 15px 본문 | 가독성은 가장 좋았으나 일반 SaaS 대시보드에 가까워져 "의도적으로 작은 범위의 도구"라는 성격이 흐려짐 |
| 유리 (Glass) | 절제된 반투명 + blur 1단계, 틴트 배경 | 사용자 요청으로 실제 제작 후 비교. 메타데이터 대비 손실이 크고 장식적으로 읽힘. Discord 자체도 blur를 쓰지 않음 |
| 지브라 행 틴트 | 목록 행을 교대로 2% 밝게 | 클립 행은 높이가 균일하지 않음(코드 블록·첨부가 있으면 3배). 교대 틴트가 리듬이 아니라 임의의 블록으로 읽혀 기각. 헤어라인 단독 유지 |
| 소스 채널별 틴트 | 채널마다 다른 틴트 | 채널 수 상한·색 배정·접근성 문제를 새로 만들어 P0 범위 밖으로 판단 |

## 3. 디자인 과정에서 교정한 판단

- **흰 캔버스 착시:** 초기 비교에서 유리 방향이 "섹션 구분이 잘 된다"고 보였으나, 실제 원인의 절반은 비교용 흰 배경이었다. 각 방향을 자기 페이지 배경 위에 다시 올려 비교한 뒤 판단이 바뀜. → 시안은 항상 실제 페이지 배경에서 검증한다.
- **접근성 결함 수정:** muted 텍스트 토큰이 WCAG AA 미달(4.0:1)이었다. `#6e737a → #83888f`, `#71767f → #7e838c`로 조정해 4.6:1 이상 확보. 비활성 컨트롤은 의도적으로 3:1 미만 유지.
- **faint 토큰 오용 방지:** `faint(#5f646a)`는 비활성 컨트롤 전용으로 용도를 한정했다. 플레이스홀더·조건 라벨·주석 등 의미를 가진 텍스트에는 `muted(#83888f, 5.37:1)`를 사용한다.
- **상태를 색만으로 전달하지 않음:** 모든 상태 표시에 텍스트 태그(`NOTE` / `OK` / `확인` / `오류` / `누락`)를 선행시킴.

## 4. 컴포넌트 라이브러리 선택

shadcn/ui 등 기성 라이브러리는 구현 속도에 도움이 되지만, 기본값을 그대로 쓰지 않고 위 토큰(표면 4단·선 3단·글자 4단·의미 4색, 4px 간격 배수, radius 2px, 그림자 없음)으로 정규화해 사용한다. 필요한 컴포넌트는 P0가 실제로 쓰는 범위로 한정: 버튼 4변형, 입력/셀렉트/역할 다중 선택, 라디오·체크박스, 배지, 상태 콜아웃, 토스트, 클립 카드, 페이지 헤더, 필터, 페이지네이션, 빈/로딩/오류/세션 만료 상태, 파괴적 동작 확인.

## 5. 카드 시각 위계 (고정)

① 출처(작성자·채널·원본 시각) → ② 메시지 본문 → ③ 답장 맥락 → ④ 보관 시각 → ⑤ 동작(secondary 1개).

반응 수·좋아요·순위 표시는 카드에 존재하지 않는다. 원본 메시지의 봇 반응(📎)은 "아카이브가 존재함"이라는 신호이며 인기 지표가 아니므로 웹 아카이브에 수치를 노출하지 않는다.

## 6. 카피 원칙 (한국어 P0)

1. 결과를 먼저, 이유는 짧게 — "채널을 선택해야 저장할 수 있습니다."
2. 내부 용어 비노출 — canonical clip / tombstone / PENDING 등은 UI에 등장하지 않음
3. 과장 금지 — "어떤 데이터도 저장하지 않습니다"가 아니라 "메시지 사본이 아니라 운영 정보를 저장합니다"
4. 파괴적 동작은 결과를 문장으로 — 삭제/유지 항목을 나열한 뒤 명시적 체크박스 확인

## 7. 디자인 중 발견한 제품/범위 이슈

- **관리 화면 분리:** 브리프는 화면 B와 E를 합칠 수 있다고 했으나, 최초 설정(1회, 결과를 읽어야 하는 흐름)과 현재 설정 열람+데이터 삭제(반복 방문, 파괴적 동작 포함)는 목적이 달라 2개 화면으로 분리했다.
- **기존 채널 사용의 노출 결과:** 기존 채널을 고르면 그 채널을 볼 수 있는 모든 멤버가 아카이브를 볼 수 있다는 사실을 선택 지점에 인라인으로 명시했다. 보안 문서를 읽지 않아도 신뢰 결과가 전달되어야 한다는 요구를 충족한다.
- **목록 누락 상태의 정보 잔존:** Discord 측 사본이 삭제된 경우에도 보관 기록(작성자·채널·시각)은 남으므로, "원본 없음"이 아니라 "보관된 사본을 찾을 수 없음 + 기록은 남아 있음"으로 문구를 분리했다.
- **설정 링크 만료 화면:** 만료 이유(일회용·15분)와 복구 경로(`/setup` 재실행)를 함께 제시하고, 이미 설정을 마친 서버라면 링크 없이도 동작한다는 안심 문구를 추가했다.

## 8. 반응형 · 접근성

- 컨테이너: 아카이브 720px, 설정 폼 560px, 복구 화면 420px, 페이지 최대 1120px
- 640px 이하: 필터·페이지네이션 세로 적층, 카드 패딩 16→12. 960px 이하: 설정 2열 → 1열
- 포커스 링 전 컴포넌트 공통(액센트 2px + offset 2px), 본문 최소 13.5px / 라벨 최소 11px, 한글 본문 line-height 1.65 이상
- 긴 코드·URL은 `pre` 내부 가로 스크롤로 격리해 카드 폭을 넘기지 않음

## 9. 마감 때문에 의도적으로 남긴 미완성

- 라이트 테마는 핵심 표면·버튼·입력·콜아웃만 검증했고 전 컴포넌트 매트릭스는 만들지 않았다
- 애니메이션은 정의하지 않았다(로딩은 정적 스켈레톤 + 텍스트 고지)
- 일러스트레이션·마케팅 페이지·아이콘 세트 없음. 첨부 미리보기는 플레이스홀더
- 워드마크는 라틴 "Clip" 단일 표기. 한글 병기 및 제품명 확정은 P1
- 스크린리더 안내(aria-live) 문구는 구현 단계에서 확정 필요

## 10. 구현 준비 단계에서 확정된 변경 (2026-08-18)

디자인 완료 후 구현 준비 과정에서 Discord API 실제 제약을 확인해 아래 항목을 조정했다. 시각 언어와 카피 원칙은 변경하지 않았다.

### 10.1 아카이브 표현: 1개 메시지 → 2개 메시지

Discord는 forward(`message_reference.type = 1`)와 함께 `content`·`embeds`·`components`를 보내면 오류 `160011`(`Forward messages cannot have additional content`)로 거부한다. 또한 forward 스냅샷 객체에는 `author`가 포함되지 않는다.

따라서 제품 스펙 §6.3의 "스냅샷 주위에 출처 메타데이터를 함께 담은 아카이브 게시물" 은 구현 불가이며, 아카이브 항목 1건은 **출처 메시지 + forward 메시지 2건**으로 구성한다.

**화면에 미치는 영향:** 없음. 화면 D의 클립 카드 위계(① 출처 → ② 본문 → ③ 답장 맥락 → ④ 보관 시각 → ⑤ 동작)는 그대로 유지된다. 카드의 출처 줄은 Discord 응답이 아니라 PostgreSQL 제어 평면(작성자·채널·원본 시각·클립 시각)에서 렌더링하고, 본문만 forward 메시지에서 가져온다. 결과적으로 행당 Discord 요청 수는 늘지 않는다.

### 10.2 보관 불가 대상 명시

Discord는 `DEFAULT`·`REPLY`·`CHAT_INPUT_COMMAND`·`CONTEXT_MENU_COMMAND` 유형만 forward할 수 있다. 투표·통화·활동·시스템 메시지는 보관할 수 없다. 봇이 볼 수 없는 채널의 메시지도 오류 `160014`로 거부된다.

새 문구를 만들지 않고 기존 "대상 오류" 문구 `이 메시지는 보관할 수 없습니다` 를 재사용한다. 카피 원칙 2(내부 용어 비노출)와 한국어 카피 확정 원칙을 유지하기 위해서다.

### 10.3 설정 토큰 만료: 10분 → 15분

제품 스펙 §5.1은 약 10분, 화면 A의 확정 한국어 카피는 `발급 후 15분` 으로 서로 달랐다. 확정된 한국어 카피가 우선이므로 스펙을 15분으로 정렬했다. 카피는 수정하지 않았다.

### 10.4 콜아웃 태그 표기

디자인 원본 HTML의 화면 A 콜아웃은 `다음` 태그를 사용하지만, 핸드오프 문서가 확정한 태그 집합은 `NOTE` / `OK` / `확인` / `오류` / `누락` 이다. 구현은 핸드오프 문서를 따라 `NOTE` 로 통일한다.

### 10.5 권한 고지 추가 필요

`VIEW_CHANNEL` 이 클립 대상 채널 전체에 대한 상시 권한임이 확인되었다(부트스트랩 전용이 아님). 화면 B의 신뢰 관련 문구는 현재 아카이브 노출 범위만 다루므로, 구현 시 설정 화면에서 이 사실을 관리자가 읽을 수 있어야 한다. 새 문구가 필요하면 이 문서에 추가로 기록한다.

### 10.6 `/setup` 권한 거부 문구 재사용

`/setup` 을 `MANAGE_GUILD` 없이 호출한 경우의 거부 문구가 핸드오프의 "Discord-side copy" 표에 없다. 표가 제공하는 유일한 거부 문구는 `이 서버에서 메시지를 보관할 권한이 없습니다` 이며, 이는 메시지 보관을 기준으로 서술되어 있어 설정 진입 거부와 정확히 일치하지는 않는다.

새 문구를 만들지 않고 이 기존 문구를 재사용한다. 10.2 와 같은 판단이다. 확정된 한국어 카피에 없는 문구를 구현 단계에서 창작하지 않는다는 원칙이 문구의 정확한 대응보다 우선하기 때문이다.

성공 응답에는 한국어 문구를 붙이지 않고 설정 링크만 보낸다. 표에 `/setup` 성공 문구가 없으므로, 링크를 감싸는 안내 문장을 쓰면 그것이 곧 새로 만든 한국어 문구가 된다.

### 10.7 4px 간격 규칙과 컴포넌트 실측값의 충돌

핸드오프 문서 73행은 간격을 "4px 배수만" 으로 규정한다. 그러나 같은 문서의 컴포넌트 명세는
5, 7, 10, 11, 13, 14, 18, 22px 을 사용한다. 버튼 `10px 16px` / `7px 12px`, 인풋 `10px 11px`,
칩 `5px 7px`, 배지 `4px 6px`, 콜아웃 `11px 12px`, 토스트 `11px 13px`, 카드 `16px 18px`
(`gap: 10px`), 화면 C 행 `12px 14px`, 화면 B `gap: 22px`. `tokens.css` 에는 이 값들에 대한
`--sp-*` 토큰이 없다.

두 규칙을 동시에 지킬 수 없다. 문자 그대로 4px 규칙을 적용하면 모든 컨트롤의 여백을 다시
설계하게 되고, 이는 확정된 디자인을 구현 단계에서 변경하는 것이다. 반대로 실측값을 그대로
쓰면 명시된 규칙을 어긴다.

**컴포넌트 실측값을 따른다.** 요약 규칙보다 구체적인 컴포넌트 명세가 우선한다. 확정된 디자인을
재설계하지 않는다는 원칙이 더 상위이고, 잘못 적용했을 때 되돌리기 어려운 쪽도 재설계 방향이기
때문이다.

다만 이 값들을 컴포넌트 CSS에 직접 쓰지 않고 `tokens.css` 에 이름 있는 토큰으로 추가한다.
"시각 값의 단일 출처" 라는 규칙 2의 실제 의도는 이렇게 유지된다. 어길 수 없는 것은 4px 부분뿐이다.

이것은 명시된 규칙에서 벗어나는 결정이므로 Ori의 확인이 필요하다. 확인 전까지 구현은 위 방침을
따르되, 되돌릴 경우 영향 범위는 `tokens.css` 의 간격 토큰과 이를 참조하는 F.3 프리미티브에
한정된다.

### 10.8 핸드오프에 없는 한국어 문구 (미해결)

F.2 문자열 테이블 작업에서 확인된, 화면이 필요로 하지만 핸드오프가 제공하지 않는 문구다.
창작하지 않고 기록만 남긴다.

1. 클립 카드 푸터 액션 — 카드 명세는 "오른쪽에 보조 액션 하나" 라고만 하고 이름을 주지 않는다.
2. 아카이브 목록 빈 상태 — 클립이 0개일 때의 문구가 없다.
3. 저장 실패 / 서버 오류 — 클라이언트 검증 문구(`채널을 선택해야 저장할 수 있습니다.`)만 있다.
   `오류` 태그는 문서 전체에서 115행 콜아웃 색상 표에 한 번 나오고, 이를 사용하는 화면이 없다.
4. 화면 B 채널 `<select>` 의 접근성 레이블 — 라디오는 `기존 채널 사용` 으로 레이블되지만
   셀렉트 자체에는 문구가 없다.

### 10.9 콜아웃 전경색 불일치: 토큰을 따른다

F.3 작업에서 확인된 두 번째 불일치다. 핸드오프 상태 콜아웃 표(112–115행)의 전경색 중
NOTE `#aeb9dc` 와 OK `#9ccdb3` 이 `tokens.css` 의 `--accent-text: #8f9fd6`,
`--success-text: #86c1a1` 과 다르다. 나머지는 모두 정확히 일치한다 — 확인 `#d6bb8f` 와
오류 `#e9a3a3` 은 각각 `--warning-text`, `--error-text` 와 같고, 네 종류의 배경색과
테두리색도 모두 대응 토큰과 같다.

**토큰을 따른다.** 10.7의 간격 문제와 결론이 반대인데, 두 상황이 다르기 때문이다.

간격은 `tokens.css` 에 해당 값이 **아예 없었다**. 단일 출처가 존재하지 않았으므로 토큰을
추가하는 것이 규칙 2의 의도를 지키는 유일한 방법이었다.

색상은 `tokens.css` 에 같은 역할의 토큰이 **이미 있고**, 네 항목 중 두 항목은 문서와 정확히
일치한다. 즉 누락된 역할이 아니라 두 문서 사이에서 값 두 개가 어긋난 것이다. 규칙 2가
`tokens.css` 를 시각 값의 단일 출처로 지정하고 있고 여기서는 그 출처가 실제로 존재하므로,
`--note-text` / `--ok-text` 를 새로 만들지 않는다.

**단, 접근성이 이 판단을 뒤집을 수 있다.** 핸드오프 값이 더 밝은 쪽이므로, 토큰 값이 각자의
콜아웃 배경 위에서 AA(4.5:1)를 넘지 못한다면 접근성 규칙이 우선한다. 구현 시 두 대비값을
계산해 기록하도록 지시했고, 미달이면 이 결정을 되돌린다.

### 10.10 10.9를 철회한다 — 콜아웃 전경색은 핸드오프가 맞다

10.9의 결론(토큰을 따른다)은 틀렸다. 근거로 삼은 추론이 잘못됐다.

10.9는 "확인과 오류는 토큰과 일치하므로 같은 역할이고, 따라서 NOTE/OK의 차이는 두 문서 사이의
값 드리프트" 라고 판단했다. 목업을 직접 확인하니 아니었다. `design/Clip P0 Screens.dc.html` 은
네 값을 모두 쓰며, 두 쌍은 서로 다른 역할이다.

- `#aeb9dc` — 콜아웃 **본문 텍스트** (`font:400 12px/1.6 … color:#aeb9dc`).
- `#8f9fd6` — 링크(`a{color:#8f9fd6}`), 5px 마커 점, 포커스 아웃라인.

즉 `--accent-text` 는 "강조색을 링크·표식으로 쓸 때" 의 값이고, 콜아웃 표면 위에 얹히는 본문
텍스트는 대비를 확보하기 위해 더 밝은 별도 값이 필요하다. `tokens.css` 에 그 역할의 토큰이
없을 뿐이다. 확인·오류가 일치한 것은 역할이 같아서가 아니라 그 두 팔레트에 텍스트 단계가
하나뿐이기 때문이다.

따라서 10.7(간격)과 같은 상황이다: 누락된 토큰이지 어긋난 값이 아니다. **핸드오프 값을 쓰고,
콜아웃 본문용 토큰을 `tokens.css` 에 추가한다.**

이 판단을 뒤집은 것은 Ori의 질문이었다. `design/*.dc.html` 을 스타일의 기준으로 삼자는 제안을
검토하려고 목업의 실제 값을 세어보다 드러났다. 요약 문서(핸드오프·토큰)끼리 비교하는 동안에는
보이지 않았고, 원본을 열자 한 번에 보였다.
