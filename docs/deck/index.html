Clip

Deliberate community memory for Discord.

A Discord bot and admin web app, scoped, built, deployed and verified by cgm-16. October 2026.

Pins were never meant to be memory

Discord pins are a short list, locked to one channel and managed by moderators. The current limit is 250 per channel.

The starting point was concrete: a community had to delete old pins to make room for new ones.

Pin count is the symptom. The gap is that a community has no low-friction way to say "this is worth keeping for us."

Clipa member with permission says this is worth preserving for the community

Clip is deliberate memory: one visible message, preserved on purpose, with no pin first, no popularity threshold and no transcript.

How it works

  1. A member right-clicks a message and picks Apps → Clip.
  2. The archive channel gets two messages: a provenance line (author, source channel, time), then a forward of the message.
  3. The original gets a 📎 marker, and its author gets a DM with a remove button. Both are best-effort: a clip still succeeds without them.

Why two messages: Discord rejects a forward that carries any content of its own (error 160011), and a forward's snapshot omits its author. So provenance has to come from Clip's own records, posted alongside.

Discord keeps the content

The central architecture decision is an ownership boundary.

Discord

message bodies · embeds, attachments, media · rendered snapshots · user and channel display names

PostgreSQL

guild configuration and allowed roles · Clip identity and state machine · per-member preservation signals · removal tombstones · setup tokens and admin sessions

Clip stores no message bodies, attachments, embed payloads, avatars, search index or embeddings. Deleting a server's Clip data erases only Clip's control state. The archive channel and every message in it stay in Discord.

Setup and the web archive

An admin runs /setup in Discord and gets a one-time link valid for 15 minutes. On the web, they choose the archive channel and the roles allowed to clip. Admins also get a read-only web archive of the server's clips.

The hard parts

  • One canonical Clip per message, under concurrency. Uniqueness is enforced by the database, and anything that depends on the clipper count takes a row lock. There is no check-then-insert. Tested against real PostgreSQL.
  • Removal wins. When the author or an admin removes a clip, that overrides every clipper and leaves a tombstone that blocks the message from being clipped again.
  • Never half-archived. A Clip never becomes active with a missing or partial archive.
  • Platform facts checked before they were built on, including 160011 (a forward cannot carry content), snapshots without author, and the four forwardable message types.
  • One slipped through. A poll arrives as an ordinary message, so it passed the type check; reading the type check found it, and a live test confirmed it, and polls are now refused before any state is written (#84).

A cut was a decision

It wasn't going to fit, so I cut the web archive and kept the Discord path and minimal setup.

Afterwards, I restored it with evidence. The web archive shipped on 2026-10-09 (PR #61). On 2026-10-14 the restoration's browser end-to-end gate passed 8/8 against production on sha-b845a59, and again on sha-3ed1d60.

How I built it

Claude Code was the implementer. I held the product and architecture decisions. During the restoration, every PR got an independent review before it opened, and every code change started with a failing test, recorded before the fix.

The failures I recorded share one shape: rigorous checking aimed one step to the side of the claim it was meant to support. The two below were caught by something other than the work that produced them: a documentation check, and a production gate.

The forward that couldn't carry its own label

What happened: an AI-written plan put provenance and the forward into one archive post.

Caught by: a documentation check before any code. Discord returns 160011 for a forward with content, and snapshots have no author.

What changed: every archive entry is two messages, and provenance comes from Clip's own records.

A reviewed fix that failed its first real run

What happened: deploy.sh pinned its rollout check to a revision number. Under the Recreate strategy, Kubernetes bumps that number only after the rollout starts, so the script read the old one and failed with desired revision (12) is different from the running revision (13). The deploy itself was healthy.

Caught by: the script's own verification gate, on production.

What changed: the script now verifies by generation, and a regression test reproduces the exact error (PR #97).
